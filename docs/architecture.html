Undo · iOS · architecture

A browser with one bookmark and three filters

Undo is not an Instagram client. It is Instagram's own mobile website, running inside an app that refuses to load some pages and hides some elements on the rest. Everything else on this page follows from that.

The one idea

We build the subtraction, not the app

Inside Undo there is a WKWebView — a complete browser engine with none of the browser's own interface around it. It loads instagram.com, signs in as you, and renders Instagram's real HTML.

That single decision is why this is achievable at all. There is no private API, no scraping, no reverse engineering, no account of ours between you and Meta. It is also how every app in this category works, Feather and ScrollGuard included.

So the list of things we never write is long, and each item is a thing that cannot break:

  • Instagram gives usLogin, including two-factor
  • Instagram gives usThe feed and stories
  • Instagram gives usDMs
  • Instagram gives usSearch and profiles
  • Instagram gives usPhoto posting
  • Instagram gives usVideo playback

What we write is the filter. It is a few hundred lines, and it is the entire product.

The mechanism

Three filters, cheapest first

A page falls through four layers. The first three are below; a fourth, added later, sits above them and removes some things from Instagram's data before the page is drawn at all — it is described in SECURITY.md rather than here.

LAYER 1

Navigation policy

About ten lines of Swift. Before any page loads, it compares the URL path against a list and cancels the load outright.

Reads
paths.json
Breaks when
Instagram changes its URLs. They have been stable for years.
If it breaks
A blocked page opens. Loud and obvious.

LAYER 2

Static hides

A stylesheet installed before the page body is parsed, so the elements it hides are never painted. Plain CSS — it points at things by href and aria-label, never by class name.

Reads
hide.css
Breaks when
A selector changes. Every few weeks is realistic.
If it breaks
The Reels button reappears in the bar.

LAYER 3

Injected script

A small script running inside the page. It watches the feed as posts arrive and hides the ones that should not be there.

Reads
feed.json + filter.js
Breaks when
Instagram redesigns the feed.
If it breaks
Suggested posts leak back in. This is the layer that needs upkeep.

Layers 2 and 3 look redundant — both hide things. They are not interchangeable. Layer 2 can only point at an element by its attributes, which is enough for a button that is always there and never enough for a sponsored post. Layer 3 can read text, but it runs after the element exists, so using it for the nav bar would mean watching the Reels button appear and then vanish on every page load. Different targets, different timing.

They do share one delivery mechanism: both are installed into the page as user scripts. That is deliberate. An Android WebView has no equivalent of WebKit's compiled rule lists, so keeping layer 2 as an ordinary stylesheet is what lets the Play Store build reuse the identical file later.

The trust story

Our code stands down on every login page

An app that embeds a website can read anything typed into it, passwords included. That is the position Feather asks you to trust an anonymous developer with. Undo is built so you can check instead. The precise claim, including where it stops short of absence, is in SECURITY.md.

Why this is checkable rather than a promise

Three things make the claim testable by a stranger:

The decision is a pure function with unit tests that run on every commit in public CI. A three-line marker script sets a flag, so anyone can open Safari's Web Inspector against the running app and confirm our code is present on the feed and absent on /accounts/login/. And the whole filter ships as plain files in the app bundle, so an installed copy can be extracted and diffed against the repo.

How the code is arranged

Rules are data; the app is dumb

The Swift app holds no filter rules of its own. Every rule is a JSON file or a plain script in engine/, which the shell reads at launch.

engine/

The filter. Plain JavaScript and JSON. No Swift.

instagram/
  paths.json   ← layer 1 blocks
  hide.css     ← layer 2 hides
  feed.json    ← layer 3 hides
  filter.js    ← layer 3 logic
  prune.json  ← data layer drops
  prune.js    ← data layer logic
marker.js      ← the guard's flag

ios/

The shell. Swift. Reads the files above.

UndoKit/       ← pure logic, tested
                 on the Mac
Undo/
  WebTab        ← builds the web view
  WebCoordinator ← layer 1 & the guard
  EngineBundle  ← reads engine/

Three things fall out of this. Changing a rule is a one-line edit to a JSON file, not a code change. The Android shell later reuses engine/ untouched. And because those files ship into the app bundle exactly as they appear in the repo, the promise "here is everything Undo does to the page" is something a stranger can verify with a diff.

Living with it

What breaks, and what it costs

Instagram will change. The design's job is to make sure that when it does, the failure is small, obvious and cheap to fix.

Failure modes by layer, worst case first for the reader who has to maintain this.
LayerBreaks whenYou noticeThe fix
Navigation Instagram moves a URL A blocked page opens One line in paths.json
Content rules A selector changes The Reels button is back One line in hide.css
Script The feed is redesigned Suggested posts leak in A phrase or selector in feed.json

None of those fixes touch Swift, and none need a rebuild of anything but the app bundle. Both test suites read the real rule files, so a typo fails on the Mac in about a second rather than on the phone in silence.

One honest limitation: the phrases the script matches — Sponsored, Suggested for you — are English. An Instagram account set to another language hides less until that language's phrases are added to feed.json.

Settled

Four decisions, and what tipped each one

These were open while the plan was written. The deciding question for all four turned out to be the same one: what does it take to publish this reliably on GitHub, the App Store and eventually the Play Store?

Layer 2 is an injected stylesheet

WebKit has a purpose-built API for this, WKContentRuleList, and the plan used it at first. Android's WebView has no equivalent.

Tipped by: the Play Store. As an ordinary stylesheet, the identical file installs the identical way on both platforms. The WebKit API returns later if Undo ever needs to stop reel video being fetched rather than merely hidden — that is something only it can do.

Explore redirects to search

The magnifier in Instagram's bottom bar points at /explore/. Blocking that path removes search along with the grid, so the plan sends the magnifier to search instead.

Tipped by: failing closed. The alternative — load the page and hide the grid with CSS — means a broken selector shows a full screen of exactly what you are avoiding. Cancelling the load cannot fail that way.

The Xcode project is hand-written

250 lines of Apple's project format, written by hand rather than clicked through Xcode's New Project dialog. It parses, builds, and resolves its package — that is verified.

Tipped by: CI. Xcode's dialog puts build schemes in a folder that git ignores, which is the classic reason a project builds locally and fails in CI. Writing the file puts a shared scheme in place from the first commit. After the first launch Xcode owns the file either way.

UndoKit stays a separate package

The pure decision logic — including the login-page guard — sits in its own small Swift package, so its tests run on a Mac in about a second with no iOS simulator involved.

Tipped by: the Play Store, again. The Android app will need this same logic in Kotlin. Having it isolated in one small package makes that a port of one file rather than an archaeology exercise across the app.
